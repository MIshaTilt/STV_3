## Детализация тестовых сценариев (Test Cases)

Ниже представлен перечень тестов, которые должны быть реализованы для проверки функционала. Тесты разделены на две логические группы: **Routes** (маршрутизация) и **Content** (наполнение и бизнес-логика представлений).

### Группа 1: Проверка маршрутизации и статусов (`test_routes.py`)

| ID | Название теста | Что проверяет | Ожидаемый результат |
| :--- | :--- | :--- | :--- |
| **TC-01** | `test_list_status_200_expected` | Доступность главной страницы каталога. | GET-запрос по имени маршрута `catalog:table_list` возвращает `status_code == 200`. Используется шаблон `catalog/table_list.html`. |
| **TC-04a**| `test_detail_status_200_expected` | Доступность детальной страницы существующего товара. | GET-запрос по `catalog:table_detail` с валидным `pk` возвращает `status_code == 200`. Используется шаблон `catalog/table_detail.html`. |
| **TC-05** | `test_detail_404_if_not_exists` | Обработка запроса к несуществующему товару. | Запрос детальной страницы с заведомо несуществующим `pk` (напр., 9999) возвращает `status_code == 404`. |
| **TC-06** | `test_about_status_200_expected` | Доступность статической страницы "О проекте". | GET-запрос по `catalog:about` возвращает `status_code == 200`. Используется шаблон `catalog/about.html`. |
| **TC-09** | `test_list_reverse_match_url` | Корректность генерации корневого URL. | Функция `reverse('catalog:table_list')` возвращает ожидаемый путь маршрута (корневой `/`). |

### Группа 2: Проверка контекста и логики представлений (`test_content.py`)

Перед запуском тестов этой группы в `setUpTestData` должны быть созданы 2 материала ("Дерево", "Стекло") и 3 стола с разными параметрами длины, веса (вкл. `null`) и брендов для валидации сортировки.

| ID | Название теста | Что проверяет | Ожидаемый результат |
| :--- | :--- | :--- | :--- |
| **TC-02** | `test_list_context_objects_not_empty` | Наличие объектов в контексте списка. | В `response.context` есть ключ `tables`, он содержит экземпляр `QuerySet`, длина списка равна количеству созданных в БД тестовых объектов. |
| **TC-03** | `test_list_filter_by_type_expected` | Логику фильтрации списка товаров. | При передаче GET-параметра `?type=<id_дерева>`, в контексте `tables` остаются только объекты, связанные с этим материалом. |
| **TC-04b**| `test_detail_context_contains_object` | Корректность передачи объекта в детальном представлении. | В `response.context` есть ключ `table`. Атрибут `brand` этого объекта совпадает с ожидаемым (по запрошенному `pk`). |
| **TC-07** | `test_about_contains_text_expected` | Рендеринг контента статической страницы. | Ответ `catalog:about` содержит HTML-текст `"О проекте"`. |
| **TC-08** | `test_list_empty_expected` | Поведение каталога при отсутствии записей в БД. | При пустой таблице `Table` контекст `tables` имеет длину 0. В HTML-ответе присутствует текст `"Товаров пока нет"`. |
| **TC-10** | `test_list_context_keys_exist` | Полноту контекста для работы фильтров в UI. | Контекст содержит `tables` (товары) и `types` (`QuerySet` всех доступных `TableMaterial`). |
| **Доп.1** | `test_list_sort_default_by_brand` | Сортировку списка по умолчанию. | Если параметры не переданы, товары в `tables` отсортированы по алфавиту по полю `brand`. |
| **Доп.2** | `test_list_sort_by_required_attr_length` | Сортировку по обязательному числовому атрибуту. | При GET-параметре `?sort=length` товары отдаются в порядке возрастания длины. |
| **Доп.3** | `test_list_sort_by_optional_attr_weight` | Сортировку по атрибуту, допускающему `NULL`. | При `?sort=weight` товары сортируются корректно (с учетом того, как БД обрабатывает `NULL`). Тест должен проверять относительный порядок объектов с заполненным весом. |
| **Доп.4** | `test_list_sort_by_type` | Защиту от невалидной сортировки (fallback). | При попытке передать неразрешенное для сортировки поле (напр., `?sort=material__name`), представление игнорирует параметр и применяет сортировку по умолчанию (`brand`). |
